What the data shows Bimodal tail

  • The page_cache + Redis distribution is bimodal. 4,499 requests landed in 0.4–0.95 s — that's while PHP-FPM workers can keep up with the queue.
  • The legacy stack hits a hard cliff. 500 requests are stranded in the 5.4–5.95 s bucket — these are the ones that hit DNS retry / connection re-establishment once the worker pool saturates. You can see it on the histogram as an empty gap from 1 s to 5 s and a sharp wall at the end.
  • Varnish has no such cliff. Even its P99 = 325 ms is lower than the legacy stack's P10 = 541 ms. That's the core advantage of serving straight from Varnish memory — the request never reaches PHP, so the worker pool simply cannot become the bottleneck.
At 5× higher concurrency (500 vs 100 in the previous run) both stacks slow per-request but the gap stays huge — Varnish completes the entire 5,000-request burst in 1.38 s while the Redis stack takes 11.03 s. All 5,000 requests served HTTP 200 on both stacks.

What the data shows Cold cache + heavier page

  • Throughput is much closer in dev than in local. Redis stack edges out by ~18% on raw req/s (501 vs 425 req/s) and finishes 1.8 s sooner. On local Varnish was 8× ahead — what changed?
  • The test was a cold start against /articles, not the homepage. /articles is a Views listing — heavier than the homepage, larger response body, larger Purge-Cache-Tags surface. The first ~500 concurrent requests all MISSed in Varnish and slammed origin's PHP-FPM at once. The Redis stack didn't have this cold-storm penalty because it was already warm from previous testing / regular traffic.
  • Varnish still wins decisively on the tail. P90 756 ms vs 1,620 ms (2.14×), P95 1,173 ms vs 1,986 ms (1.69×). With real-world traffic and a warm cache, the P50/P90 picture flips much more strongly in Varnish's favour — the synthetic 500-cold-MISS storm is a worst case.
  • Both stacks have heavy tails. Both histograms have ~13% of responses in the 1–5+ second range. Likely PHP-FPM worker saturation at the origin under -c 500, plus DNS+dialup outliers (one request on each side over 5 s spent its time in the connection-setup phase, not Drupal). On the homepage the same effect is much smaller because the response is tiny and cached more deeply.
This test stresses the worst case for Varnish: cold cache + simultaneous burst of 500 concurrent fresh requests. The Redis stack's apparent advantage on raw req/s comes from already being warm and from /articles being heavy enough to expose the cold-start penalty. A more representative run would issue a few warm-up hits first (or run the same test twice and compare the second pass); under those conditions Varnish wins both throughput AND tail, like in the local DDEV tab. All 5,000 requests on both endpoints returned HTTP 200.
